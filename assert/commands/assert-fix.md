description: Work the Assert audit task list. Fix findings through the Assert MCP server, verified by the next scan
---
Use the Assert MCP server to work this repository's audit task list. Your agent knows it as **assert**, or by the name you gave the server when you added it.

**The goal: every finding this scan reported is looked at and given the right ending — fixed, disputed or accepted.** Not a dimension, not the high-impact part: all of it. `next_task` serves one **cause** at a time — the argument a group of findings share, not one instance — already ranked by impact ÷ effort. That ranking decides the ORDER you work in. It never decides how much of the queue you work, and it never decides WHAT you change.

**Fix the root cause, always.** Before you edit, describe the defect without the detector — in words an engineer who has never seen Assert would recognise. If the only description is "it is flagged" or "it is over the threshold", the code is fine: dispute or accept, don't change it to silence it. Dead or superseded code is deleted, never annotated, split or reworded. Appeasement is not a fix however clean the diff: splitting a body only to get under a number, moving a comment to satisfy a rule, relabelling a file as generated or vendored when it isn't, a test that still passes with the repair it claims to pin reverted.

Loop:
1. Call `audit` — the grade, each lens, the remediation plan, and a `queue` block saying how much work is actually left. **The plan is a menu, not a progress bar:** it lists what the scan found and keeps listing it after the work is done. The `queue` block is the honest counter.
2. Call `next_task` — the next cause, fully briefed: what the dimension measures, its current /10, the estimated point-gain + effort, **what to do**, the instances under that cause (file:line + fingerprint), the `causeKey`, and a `progress` block. A packet carries at most 50 instances; when a cause has more, it says so — work them and call again, and the next packet carries the ones still open. (Or `get_task("D34")` for a specific dimension.)
3. Give the cause **one of three endings**, then move on:
   - **Fix it** — change the code for every instance, then `resolve_finding` each with a short note. Resolution is provisional: the next scan is the arbiter, so never claim a fix you didn't make. On a **threshold** finding (complexity, size, counts) the finding clears only when the measured number crosses the bar the finding names — measure it the way the finding's detail defines it, on the code you actually committed, and resolve only when it is under. "Made it smaller" is not a fix.
     If the fix moves code or adds a reference across modules, call `get_architecture` (with `module` for the one you are touching, `path` for its co-change partners) **before** you change it, and `check_dependencies` on `git diff -U100000 <baseline.commit>` **before** you resolve. A `drift: true` result means the fix closed a cycle or pointed a layer outward — rework it, or say in your note why the dependency is intended.
   - **Dispute it** — `dispute_finding` if the finding is *wrong* (it isn't there) or is *noise* nobody should ever be shown. A human reviews it and it improves the detector.
   - **Accept it** — `set_cause_disposition(dimension, cause, "Accepted", note)` if the finding is **correct** and you are deliberately not acting: a considered trade-off, a cost not worth the risk, a rule that doesn't fit this codebase's job. A note is required. Your acceptance is **provisional**: it holds until the result's `expiresAt`, and stands longer only if the repository owner approves it on the findings page — so every acceptance goes in your report for them.
4. Call `next_task` **again**, every time. Repeat until it returns null, then `request_rescan` (if this repo allows it) to verify.

Rules:
- **Only a null `next_task` ends the loop.** Don't stop because the last task felt like the big one, because the plan in `audit` looked covered, or because you judged the rest low-value. Ask `next_task`.
- **Never narrow the goal.** A plan, a loop prompt, a hand-off or a resume note you write states the goal above in full — never a sub-task such as "finish the complexity rows". A session that resumes from your note works on what the note says, so a note that names one dimension turns the whole job into that dimension.
- **Leaving a cause open is not an outcome.** Every cause gets fixed, disputed or accepted. An unfixed, undecided cause comes back on every future scan of this repository, and teaches us nothing.
- **Accepted vs disputed is about whether we are RIGHT, not about whether you will act.** Both mean "not fixing it". Dispute says the finding shouldn't exist; accept says it should exist and you're living with it. Guessing wrong in either direction costs us the signal — if the detector is correct and the row is worth showing, accept it, don't dispute it.
- **In a noise dispute, name the signal the scanner could have used** — the evidence it already had and didn't act on: the fixture path, the justification comment above the row, a zero violation count, `IsPackable=false`, a test-scoped glob, a `generated_code = true` section. A dispute that says "this is fine here" buys one exemption; one that names the signal fixes the rule for everyone.
- **In a WRONG dispute, pass `evidence`** — the verbatim text at the cited line, quoted exactly as it stands in the file. The maintainer triages without your repo checked out: a false-positive claim they cannot reproduce is likely declined as unverifiable, and a decline is final in this channel.
- **In an acceptance note, say why it doesn't apply HERE.** That sentence is read across every repository that accepts the same dimension, and it is how we learn which findings are true but not worth surfacing. "Won't fix" tells us nothing; "these are generated mappers, extracting them would fight the generator on every regen" tells us to look at the generated-code gate.
- Keep a running tally of the causes you closed and how — fixed / disputed / accepted — together with `progress.instancesRemaining`, and re-state it each time round. It is what you report at the end, and it makes a stalled loop obvious.
- **Stall guard:** if `next_task` hands you the same cause twice with nothing resolved or decided in between, stop and say so — that's a server-side fault, not a finished queue. A packet whose `instances` list is empty is NOT a fault if `kind` is `"posture"` (see below).
- **Posture tasks** (`kind: "posture"`) carry no instances by design: the dimension measures the *absence* of something — a configuration, a mechanism, a document — so there is no fingerprint and nothing to `resolve_finding`. The brief is the work. Close it with `set_cause_disposition` against `causeKey: "__posture__"`, or it is handed out again on every call.
- **Decline-blocked findings are ordinary work.** A declined dispute means a maintainer read your argument and confirmed the finding is real; it is queued alongside everything else on the same impact key, with the maintainer's reasoning attached as `maintainerNote`. Read that before acting. Fix it if you can, or accept it with a note — re-disputing is refused.
- If you run low on context, or something outside the loop stops you, before the queue clears: write the goal above, the `progress` block and your tally, so the next session resumes the whole job instead of a piece of it.
- If an **advisory** finding (`advisory: true`, which does not affect your score) looks wrong, it can't be disputed; use `flag_advisory` with a note so we can improve it. Advisory findings are not served by `next_task` — they never move the score, so they are not the loop's job.
- Suppressing a finding **in the code** — an inline suppression, an ignore entry, a config exemption — is a human decision, never yours. Disputing and accepting are not that, and are expected.
- **When one root cause fans out over many instances, file it as ONE dispute.** Pass the extra fingerprints as `siblingFingerprints`: one group, one reason, one maintainer decision, and **one** call against the hourly limit instead of N. (An acceptance is already one call per cause — that is what the cause grain is for.)
- `dispute_finding` is capped at **60 submissions per hour per key** (a group counts as one). Rejected over-cap calls are not recorded, so nothing is lost but time.
- If you spot a real problem Assert missed, `report_detector_gap` with evidence.

When you're done — when `next_task` has returned null — summarize: the causes you fixed, the ones you disputed and why, and the ones you accepted and why — the accepted ones as a list the owner can approve on the findings page. If this repo allows it, call `request_rescan` to verify; otherwise tell me to run a scan.
